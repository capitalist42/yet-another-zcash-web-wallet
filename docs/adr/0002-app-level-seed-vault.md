# Seed custody lives in an app-level vault, not the SDK store

`zcash.js` persists its SQLite DB (OPFS) in plaintext and exposes no encryption hook — SyncAccessHandle is synchronous, so WebCrypto interception is impossible without patching the runtime — but it also never persists spending keys: `accounts.create` hands back a memory-only `MemorySigner`, and `attachSigner`/`detachSigner`/`restoreSigner` are the re-attachment path. We decided spend authority lives only in an app-level Vault: PBKDF2-SHA256 (210k, random salt, user-chosen passphrase) → AES-GCM-256 envelope in IndexedDB, created at wallet creation ("Remember on this device (encrypted)"), or never stored at all ("Never store" — re-enter seed to send). Restore always writes a device-keyed AES-GCM envelope (random key kept in that record; no user vault passphrase) and unlocks without asking for one. The SDK DB stays plaintext at rest: acceptable for funds (it holds no spend authority) but a metadata surface, disclosed in the README. Consequences: a fresh browser needs only the seed (not the Vault passphrase) to restore; the Vault guards the seed at rest on a device, not the unlocked session — once unlocked, the page is the security boundary.
